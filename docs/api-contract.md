# API-контракт

## Предметная область

Организация социального взаимодействия попутчиков в поездах дальнего следования.

- Главная сущность — поездка (Trip).
- Справочник — тип вагона (Carriage).
- Поле-ссылка на справочник — `carriageId`.
- Основной путь API — `/api/trips`.
- Формат обмена данными — JSON.

## Таблица запросов

| Метод и путь | Тело | Успех | Возможная ошибка |
|---|---|---|---|
| GET /api/trips | — | 200, массив или [] | 500 |
| GET /api/trips/{id} | — | 200, объект | 404, 500 |
| POST /api/trips | title, carriageId, description | 201, созданная поездка | 400, 500 |
| PATCH /api/trips/{id}/assignee | assigneeUserId | 200 | 400, 404, 409, 500 |
| PATCH /api/trips/{id}/status | status | 200 | 400, 404, 409, 500 |
| GET /api/carriages | — | 200, массив типов вагонов | 500 |
| GET /api/users | — | 200, массив пользователей | 500 |

Допустимые статусы: `New`, `InProgress`, `Closed`, `Cancelled`.

Отмена поездки — перевод в статус `Cancelled`, а не удаление строки из базы данных.

Клиент не присылает при создании `id`, `number`, `status`, `createdByUserId` и `assigneeUserId`. Их определяет сервер.

При создании поездки статус устанавливается в `New`, проводник не назначен (`assigneeUserId = null`).

## Пример JSON — POST /api/trips

```json
{
  "title": "Москва — Казань",
  "carriageId": 4,
  "description": "Ночной поезд, ищем попутчиков для общения."
}
```

## Пример ответа — 201 Created

```json
{
  "id": 9,
  "number": "TMP-639000000000000000",
  "title": "Москва — Казань",
  "description": "Ночной поезд, ищем попутчиков для общения.",
  "status": "New",
  "carriageId": 4,
  "createdByUserId": 1,
  "assigneeUserId": null
}
```

Значения `id` и `number` приведены для примера. Фактические значения формируются сервером.

## Справочник вагонов — GET /api/carriages

Код ответа: 200 OK.

```json
[
  {
    "id": 1,
    "name": "Плацкарт",
    "type": "economy"
  },
  {
    "id": 2,
    "name": "Купе",
    "type": "comfort"
  },
  {
    "id": 3,
    "name": "СВ",
    "type": "business"
  },
  {
    "id": 4,
    "name": "Тихий вагон",
    "type": "quiet"
  }
]
```

Справочник загружается из PostgreSQL.

Признак тихого вагона определяется значением `type = quiet`.

## Справочник пользователей — GET /api/users

Код ответа: 200 OK.

```json
[
  {
    "id": 1,
    "fullName": "Иванов Иван",
    "role": "passenger"
  },
  {
    "id": 2,
    "fullName": "Петрова Анна",
    "role": "passenger"
  },
  {
    "id": 3,
    "fullName": "Сидоров Константин",
    "role": "conductor"
  },
  {
    "id": 4,
    "fullName": "Администратор",
    "role": "admin"
  }
]
```

Допустимые роли:

- `passenger` — пассажир;
- `conductor` — проводник;
- `admin` — администратор.

## Пример — PATCH /api/trips/{id}/assignee

```json
{
  "assigneeUserId": 3
}
```

Назначение проводника выполняется отдельно от изменения статуса.

При назначении проводника текущий статус поездки не изменяется.

Назначаемый пользователь должен существовать и иметь роль `conductor`.

Назначение создателя поездки ответственным за собственную поездку запрещено.

Назначение проводника на завершённую или отменённую поездку запрещено.

## Пример — PATCH /api/trips/{id}/status

```json
{
  "status": "InProgress"
}
```

## Допустимые переходы статусов

| Текущий статус | Новый статус | Целевая роль |
|---|---|---|
| New | InProgress | Назначенный проводник |
| InProgress | Closed | Назначенный проводник |
| New | Cancelled | Пассажир, создавший поездку |

Перед переходом в `InProgress` необходимо назначить проводника.

Статусы `Closed` и `Cancelled` являются конечными.

Недопустимый переход возвращает 409 Conflict.

## Валидация при создании поездки

| Поле | Требование |
|---|---|
| title | Обязательное, от 5 до 80 символов |
| carriageId | Положительное целое число, существующее в справочнике |
| description | Обязательное, от 10 до 500 символов |

Пробелы в начале и конце маршрута и описания удаляются. Длина проверяется также после удаления пробелов.

При некорректных данных сервер возвращает 400 Bad Request. Поездка не создаётся.

Ошибки API возвращаются в формате ProblemDetails или ValidationProblemDetails.

Пример ответа при нарушении бизнес-валидации:

```json
{
  "title": "Некорректные данные",
  "status": 400,
  "detail": "Тема должна содержать от 5 до 80 символов."
}
```

## Коды ответов HTTP

| Код | Значение |
|---|---|
| 200 | Запрос успешно выполнен |
| 201 | Поездка успешно создана |
| 400 | Некорректные входные данные |
| 404 | Поездка не найдена |
| 409 | Конфликт состояния поездки или нарушение бизнес-правил |
| 500 | Внутренняя ошибка сервера |

Коды 401 Unauthorized и 403 Forbidden предусмотрены для последующей реализации авторизации и разграничения доступа.

## Целевое разграничение доступа

- Пассажир создаёт поездки и отменяет собственные поездки в статусе New.
- Администратор назначает проводника.
- Проводник изменяет статус только назначенных ему поездок.
- Самостоятельное назначение себя ответственным запрещено.

## Состояние реализации

На текущем этапе реализованы:

- получение списка поездок;
- получение поездки по идентификатору;
- создание поездки;
- назначение проводника;
- изменение статуса;
- получение справочников вагонов и пользователей;
- проверка входных данных;
- проверка существования связанных записей;
- проверка роли назначаемого проводника;
- проверка допустимых переходов статусов;
- хранение данных в PostgreSQL;
- подключение frontend к реальному API.

Полноценная авторизация и проверка прав текущего пользователя требуют дополнительной реализации. При создании поездки идентификатор пользователя передаётся через обязательный HTTP-заголовок X-User-Id. При отсутствии заголовка, некорректном идентификаторе или отсутствии пользователя в базе данных сервер возвращает 400 Bad Request.

Актуальная спецификация OpenAPI находится в `docs/api-collection/swagger.json`.
